# Figma 디자인 검증 Skill

## 이 Skill의 목적

`figma-implement`로 작성된 코드(또는 다른 경로로 만들어진 UI 코드)가 실제 Figma 디자인과
일치하는지 **사후 검증**한다. 추출 시점 이후 디자인이 업데이트되었거나, 구현 중 누락이
있었을 가능성을 확인하는 단계다.

> **핵심 규칙:** 메인 에이전트는 Figma MCP를 직접 호출하지 않는다.
> 서브에이전트가 **최소 범위**로 재호출하고, 메인에는 **diff 보고만** 반환한다.

```
[메인 에이전트] → 검증 대상 식별 (URL + 코드 경로 + 검증 항목)
                  ↓
              [서브에이전트]
              Figma MCP 최소 호출 (get_metadata / get_screenshot 우선)
              현재 코드와 비교
              diff 리스트만 반환 (수 KB)
                  ↓
[메인 에이전트] ← "일치/불일치 + 사유" 구조화 응답 수신
              사용자에게 보고, 필요 시 수정 제안
```

---

## 언제 이 Skill을 사용하는가

- `figma-implement` 완료 직후, 사용자에게 "디자인 일치 여부"를 보고해야 할 때
- 사용자가 "정말 디자인과 일치하는지 확인해줘", "다른 부분 있으면 수정해줘"라고 요청할 때
- 디자인 업데이트가 의심될 때 (Figma 노드 ID가 새로 공유되거나, 추출 시점이 오래됨)
- PR 직전 리뷰어 대신 1차 시각/구조 검증이 필요할 때

---

## "최소 범위"의 정의

이 Skill의 핵심은 Figma MCP **재호출 자체를 막는 것이 아니라**,
재호출의 **범위를 좁혀서** 메인 컨텍스트와 서브 토큰을 동시에 절약하는 것이다.

### 1. 도구 수준 — 어떤 MCP를 쓰는지

| 도구 | 응답 크기 | 우선순위 | 용도 |
| --- | --- | --- | --- |
| `get_metadata` | 수십 KB | **1순위** | 구조/레이아웃/children 카운트 확인 |
| `get_screenshot` | 이미지 1장 | **1순위** | 시각 비교 |
| `get_variable_defs` | 작음 | 2순위 | 토큰값(색상/간격) 확인 |
| `get_design_context` | 500KB~2MB | **최후 수단** | 위 도구로 해결 안 되는 좁은 노드만 |

`get_design_context`는 **검증 단계에서 호출하지 않는 것이 기본값**이다.
정말 필요한 경우(예: 인터랙션 레이어 코드 의도 재확인) 좁은 자식 노드 ID로만 호출한다.

### 2. 노드 수준 — 어디를 부르는지

전체 프레임이 아니라 **의심되는 자식 노드**만 조회한다.
예: 다이얼로그 전체(`45015-350239`)가 아니라 TabsList 자식 노드만.

### 3. 비교 범위 — 무엇을 비교하는지

서브에이전트에 **체크리스트 형태의 구조화된 질문**을 준다.
"전체 일치 여부" 같은 무한 작업은 금지.
응답도 자유 서술이 아니라 **표 형식의 diff 리스트**로 받는다.

## Step 1: 정보 수집

서브에이전트를 띄우기 **전에** 다음 정보를 확정한다.

1. **Figma URL 또는 노드 ID** (검증 기준이 되는 디자인)
   - `docs/specs/{기능명}/index.md`의 메타 정보에서 자동 추출 가능하면 우선 사용
   - 사용자가 새 URL을 줬으면 그 URL 사용 (디자인 업데이트 가능성)
2. **검증 대상 코드 경로** (파일 또는 디렉토리)
   - `docs/specs/{기능명}/index.md`의 "대상 코드 위치"에서 추출 가능
   - 없으면 사용자에게 묻거나 `src/`에서 탐색
3. **검증 모드**
   - **fast** (기본): metadata + screenshot 기반 구조/시각 비교
   - **deep**: 특정 영역에 대해 `get_design_context`까지 호출 (사용자가 "정밀 검증" 요청 시)
4. **검증 범위 힌트** (선택)
   - 사용자가 "탭 부분만", "다이얼로그 헤더만"처럼 좁혀주면 그대로 전달

> 서브에이전트는 사용자와 직접 대화할 수 없으므로, 필요한 정보를 모두 수집한 후에 실행한다.

### Step 1-1: 사전 체크

서브에이전트를 띄우기 전에 아래를 확정한다:

- 검증 대상 코드 파일이 실제로 존재하는가
- Figma URL/노드 ID가 유효한 형식인가
- (스펙이 있는 경우) `docs/specs/{기능명}/index.md`의 추출 시점과 사용자가 준 URL의 노드 ID가 다르면 **디자인 업데이트 가능성**으로 표시

세부 blocker 기준은 [references/failure-handling.md](./references/failure-handling.md)를 따른다.

## Step 2: 서브에이전트로 검증 실행

Agent 도구로 서브에이전트를 생성한다.

**프롬프트 구성:**

```
Agent({
  description: "Figma-코드 일치 검증",
  prompt: `
    Figma 디자인과 현재 코드의 일치 여부를 검증하는 작업입니다.

    먼저 .claude/skills/figma-verify/figma-verify-rules.md 파일을 읽고
    그 규칙에 따라 검증을 진행하세요.
    blocker나 완료 보고가 필요하면
    .claude/skills/figma-verify/references/failure-handling.md 와
    .claude/skills/figma-verify/references/validation.md 도 읽으세요.

    ## 작업 정보
    - Figma URL: {URL 또는 노드 ID}
    - 검증 대상 코드: {파일/디렉토리 경로 목록}
    - 검증 모드: {fast 또는 deep}
    - 검증 범위 힌트: {사용자가 준 힌트 또는 "전체"}
    - 관련 스펙 (있으면): docs/specs/{기능명}/

    ## 핵심 제약 (반드시 지킬 것)
    1. get_design_context는 fast 모드에서 호출 금지. deep 모드에서도 좁은 자식 노드 ID로만.
    2. 페이지/프레임 통째로 조회 금지. 의심 노드만 콕 집어서.
    3. 응답은 자유 서술 금지. 표 형식 diff 리스트로 반환.
    4. 일치하는 항목은 카운트만 보고. 자세한 묘사 금지.

    ## 완료 시 보고할 내용
    - 호출한 MCP 도구 목록과 노드 ID (감사용)
    - 검증한 항목 수 / 일치 / 불일치 카운트
    - 불일치 항목 표 (위치, 디자인 값, 코드 값, 추정 원인)
    - 디자인 업데이트로 추정되는 항목 (스펙과도 다르면 표시)
    - 추가 정밀 검증이 필요하다고 판단되는 영역 (선택)
  `
})
```

---

## Step 3: 결과 보고 및 후속 처리

서브에이전트가 반환한 diff 보고를 사용자에게 그대로 전달하되, 다음을 추가한다:

1. **메인이 직접 확인한 코드 라인 링크**
   - diff 항목의 파일 경로/라인을 markdown 링크로 변환해 사용자가 바로 이동 가능하게
2. **수정 제안 여부 확인**
   - diff가 있으면 "위 항목 수정할까요?"를 묻는다 (자동 수정하지 않는다)
   - 사용자 승인 후 `figma-implement`의 수정 모드 흐름으로 진행

자동 검증 형식과 보고 템플릿은 [references/validation.md](./references/validation.md)를 따른다.

---

## Figma MCP 재호출 가이드

서브에이전트가 호출 결정을 내릴 때 따르는 우선순위:

```
시각적 차이 의심 → get_screenshot
구조/개수/배치 의심 → get_metadata
색상/크기 토큰 의심 → get_variable_defs
위 도구로 해결 안 되는 단일 자식 노드 → get_design_context (deep 모드만)
```

**페이지 전체 재추출은 절대 금지.** 그 작업이 필요하다는 판단이 들면 사용자에게 보고하고
`figma-extract`로 안내한다 (재추출은 verify의 책임이 아님).

---

## 핵심 원칙

1. **재호출 자체는 허용하되 범위를 좁힌다.** 이것이 이 Skill의 존재 이유다.
2. **메인 에이전트는 Figma MCP를 직접 호출하지 않는다.** 서브에이전트가 격리해서 호출한다.
3. **`get_design_context`는 최후 수단이다.** fast 모드에서는 사용 금지.
4. **응답은 구조화된 diff만.** 자유 서술 보고는 금지.
5. **일치 항목은 카운트만, 불일치 항목은 상세히.** 비대칭으로 정보 압축.
6. **자동 수정하지 않는다.** diff 보고 후 사용자 승인을 받고 별도 흐름으로 수정.
7. **재추출이 필요하면 verify가 직접 하지 않는다.** `figma-extract`로 안내한다.
