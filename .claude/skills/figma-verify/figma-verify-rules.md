# Figma 디자인 검증 규칙

> 이 파일은 서브에이전트가 읽는 검증 규칙이다.
> 직접 실행하지 않는다. `/figma-verify` Skill이 서브에이전트를 생성할 때 이 파일을 참조시킨다.

---

## 전달받는 정보

서브에이전트는 다음 정보를 프롬프트로 전달받는다:

- Figma URL 또는 노드 ID
- 검증 대상 코드 경로(들)
- 검증 모드 (fast / deep)
- 검증 범위 힌트 (전체 또는 특정 영역)
- 관련 스펙 디렉토리 경로 (있는 경우)

## 핵심 제약

다음은 어떤 상황에서도 어기지 않는다:

1. **`get_design_context`는 fast 모드에서 호출 금지**. deep 모드에서도 페이지/프레임 단위가 아닌 좁은 자식 노드 ID에만 사용한다.
2. **페이지 단위 재조회 금지**. 의심 노드만 콕 집어 조회한다.
3. **응답에 자유 서술 금지**. 표 형식의 diff 리스트만 반환한다.
4. **일치하는 항목을 묘사하지 않는다**. 카운트만 보고한다.
5. **코드를 수정하지 않는다**. 검증과 보고만 한다. 수정은 메인 에이전트의 후속 흐름이다.
6. **토큰명/스펙 텍스트 매칭만으로 "일치" 확정 금지**. 모든 in-scope 항목은 `metadata`, `screenshot`, `variable_defs` 중 항목 성격에 맞는 직접 근거로 판단한다. "스펙에 X라고 적혀 있고 코드에도 X가 있으니 일치"는 false-positive를 양산한다. border, spacing, alignment, radius, 구분선처럼 시각 차이 가능성이 큰 항목은 screenshot 근거를 우선한다.
7. **scope 힌트 해석 — 판단에 직접 영향을 주는 인접 레이아웃만 포함한다**. 사용자가 "border만", "헤더만"처럼 좁혀도, 해당 판단에 직접 연결된 컬럼/행 구분선, 들여쓰기, 정렬, padding 비율은 함께 확인한다. 별도 대규모 검증으로 확장하지 않으며, scope 밖의 명백한 발견만 `layout-adjacent`로 등재한다.
8. **사용자 시각 힌트와 직접 관찰이 충돌할 때 사용자 관찰을 우선 등재한다**. 사용자가 "X가 있다"고 명시한 시각 요소(구분선, 정렬, border 등)를 sub-agent가 screenshot에서 식별하지 못하면, "match"나 "확인 안 됨"으로 묻지 말고 **무조건 `layout-adjacent`로 등재**한다. 보고에 "사용자 힌트: X 존재 / sub-agent 관찰: 식별 안 됨 / 충돌 → 사용자 관찰 우선"을 명시하고, deep 모드 또는 사용자 결정으로 후속 흐름을 넘긴다. sub-agent의 시각 인지 한계는 figma-verify의 알려진 false-negative 패턴이며, 사용자가 직접 본 화면이 더 신뢰할 수 있다.

## Step 1: 검증 대상 정리

### 1-1. 코드 읽기

전달받은 코드 경로의 파일들을 모두 읽는다. 디렉토리가 주어지면 관련 `.tsx` / `.ts` 파일을 찾아 읽는다.

이 단계에서 다음을 추출한다:

- 컴포넌트 트리 구조
- 사용된 Tailwind 클래스 / arbitrary value
- 목업 데이터 구조 (배열 길이, 텍스트, 날짜 포맷 등)
- 조건부 렌더링 분기

### 1-2. 스펙 읽기 (있는 경우)

`docs/specs/{기능명}/index.md`가 있으면 메타 정보를 읽는다:

- 추출 시점
- 추출에 사용된 Figma URL/노드 ID
- 대상 코드 위치

이를 사용자가 준 URL과 비교해 **디자인 업데이트 가능성**을 추정한다.
- 노드 ID가 같으면: 단순 구현 누락 가능성이 높음
- 노드 ID가 다르거나 추출 시점이 오래되었으면: 디자인 업데이트 가능성이 높음

이 추정은 보고 표의 "추정 원인" 컬럼에 반영한다.

### 1-3. 검증 체크리스트 작성

코드와 (있다면) 스펙을 보고, 검증할 항목을 체크리스트로 만든다. 검증 범위 힌트가 있으면 그 범위로 좁힌다.

체크리스트 항목 예시:

- [ ] 다이얼로그 너비 / 패딩
- [ ] 탭 레이아웃 (균등 분할 여부)
- [ ] 테이블 헤더 컬럼 구성
- [ ] 목업 row 개수
- [ ] 목업 텍스트/날짜 포맷
- [ ] 색상 토큰 (primary / disabled / red 등)
- [ ] 아이콘 종류 / 자리

체크리스트는 **fast 모드 기준 10~15개 이내**로 제한한다. 너무 길면 한 번에 검증하지 말고 우선순위 상위만 잡는다.

## Step 2: Figma MCP 최소 호출

체크리스트의 각 항목에 대해 어떤 MCP 도구가 필요한지 결정한다.

### 도구 선택 매트릭스

| 의심 항목 | 1차 도구 | 2차 도구 (필요 시) |
| --- | --- | --- |
| 시각적 인상, 전반적 일치 | `get_screenshot` | - |
| 레이아웃 구조, children 카운트, layout 모드 | `get_metadata` | `get_screenshot` |
| 색상값, 간격값, 토큰 | `get_variable_defs` | - |
| 텍스트 / 목업 데이터 | `get_metadata` | - |
| 인터랙션 의도, 코드 hint | `get_design_context` (deep 모드만) | - |

### 호출 횟수 가이드

- **fast 모드**: 최대 3회 (`get_screenshot` 1회 + `get_metadata` 1~2회 + 필요 시 `get_variable_defs` 1회)
- **deep 모드**: 최대 5회. `get_design_context`는 좁은 자식 노드에만 1~2회

이 한도를 넘으면 호출을 중단하고, 미검증 항목은 보고에 명시한다.

### 노드 범위 좁히기

가능하면 페이지/프레임 ID가 아니라 의심되는 자식 노드 ID로 호출한다. 자식 노드 ID는 `get_metadata` 응답에서 추출할 수 있다.

자식 노드 ID를 모르면 최초 1회는 전달받은 프레임/섹션 노드에 대해 `get_metadata` 또는 `get_screenshot`을 호출해 범위를 좁힌다. 이 호출은 하위 노드 식별을 위한 것이며, 페이지 전체 재추출로 확장하지 않는다.

예: 다이얼로그 전체 노드(`45015-350239`)가 아니라
- TabsList 자식 노드만
- 특정 테이블 row 노드만

### get_metadata가 children을 반환하지 않을 때 (인스턴스 노드 등)

이 경우는 가장 흔한 false-positive 원인이다. **토큰/스펙 일치만으로 검증을 끝내지 않는다.**

1. **screenshot 시각 검증으로 보완**한다 — 해당 항목이 시각 판단을 필요로 하면 `get_screenshot`을 호출하고, 다음을 확인한다:
   - 컬럼 사이 **세로 구분선**의 유무 (특히 테이블 헤더/바디)
   - 행 사이 **가로 구분선**의 유무
   - 트리뷰의 들여쓰기 — checkbox/icon이 들여쓰기 대상인지 정렬 유지 대상인지
   - border가 **외곽 전체**에 둘러져 있는지 부분만 있는지
2. screenshot으로도 판단이 어려운 단일 영역은 `layout-adjacent`로 보고하고 deep 모드 권장으로 명시한다.
3. **이 fallback 없이 "스펙과 일치"로 결론 내는 것을 명시적으로 금지한다.** 보고에 "metadata 인스턴스 노드라 children 미수신 → screenshot 시각 검증으로 보완"을 기록한다.

## Step 3: 코드와 비교

각 체크리스트 항목에 대해 다음을 수행한다:

1. Figma 응답에서 해당 값을 추출한다 (예: TabsList의 `layoutMode: "HORIZONTAL"`, `primaryAxisSizingMode: "FIXED"`, children 2개)
2. 코드에서 같은 영역의 값을 추출한다 (예: `<TabsList className="grid grid-cols-2 w-full">`)
3. 두 값이 의도상 일치하는지 판단한다

### 일치 판단 기준

- **수치 차이가 의도된 매핑인가**: `font-size 14px` → `text-sm`은 일치 (Tailwind 기본 매핑)
- **레이아웃 의도가 같은가**: 균등 분할이면 `grid-cols-2 w-full` 또는 `flex-1`+`flex-1` 모두 일치
- **목업 데이터 fidelity**: 폴더 개수, 텍스트, 날짜 포맷이 디자인과 같은지 (디자인의 목업 데이터도 의도일 수 있음)
- **placeholder 처리**: 코드에서 placeholder 컴포넌트(`Icons.Database` 등)를 쓰고 있으면 unknowns로 분류

### 직접 근거 의무 (false-positive 차단)

토큰명/스펙 텍스트가 같다고 해서 일치 처리하지 않는다. 모든 in-scope 항목은 항목 성격에 맞는 직접 근거를 가져야 한다:

- 구조/개수/텍스트: `get_metadata`
- 색상/토큰값: `get_variable_defs`
- 시각적 배치/간격/구분선/border/radius: `get_screenshot`

특히 screenshot으로 확인해야 하는 항목:

- **컬럼/행 구분선의 유무 및 방향** — 가로선만 있는지, 세로선도 있는지, 헤더/바디 분리선까지 있는지
- **체크박스/아이콘의 수평 정렬** — 트리뷰의 들여쓰기 시 부모와 자식의 시작 픽셀이 동일한지
- **padding과 들여쓰기의 상대 비율** — `pl-8`이 적절한 들여쓰기인지, 아니면 정렬 깨짐인지
- **border-radius의 시각적 일치** — `rounded-md`(6px)와 `rounded-sm`(4px) 차이는 토큰명 매핑만으로는 알 수 없음
- **외곽 border의 적용 범위** — 4면 모두인지 일부만인지

각 항목에 대해 보고에 **직접 근거 1줄**을 명시한다.
근거가 비어 있는 항목은 "검증 안 됨"으로 처리한다 ("일치"가 아니다).

### 불일치 분류

| 분류 | 의미 | 처리 |
| --- | --- | --- |
| `discrepancy` | 디자인과 코드가 명백히 다름 | 표에 등재, 수정 제안 |
| `design-updated` | 스펙과도 다름 (디자인이 추출 이후 변경됨) | 표에 등재, 재추출 권유 |
| `placeholder` | 코드가 placeholder를 쓰고 있음 (자산 미확정) | 카운트만, "사후 작업"으로 분류 |
| `layout-adjacent` | scope 힌트와 인접한 레이아웃 차이 (border 점검 중 발견된 컬럼 구분선/정렬/들여쓰기 등) | 표에 등재, "scope를 넘었지만 명백한 차이로 보고" 명시 |
| `acceptable` | 의도된 매핑(Tailwind 스케일 등). **단, 항목 성격에 맞는 직접 근거를 통과한 경우만** | 일치로 처리 |

## Step 4: 결과 보고

`references/validation.md`의 보고 템플릿을 따른다.

핵심:
- 호출한 MCP 도구 목록과 노드 ID (감사용)
- 검증 항목 수 / 일치 / 불일치 카운트
- 불일치 항목 표
- 디자인 업데이트 추정 항목
- 미검증 항목 (호출 한도 초과 등)

**일치 항목을 묘사하지 않는다.** "X도 일치했고 Y도 일치했고…" 같은 서술은 보고를 부풀린다.

## 실패 처리

검증 도중 blocker가 생기면 조용히 우회하지 않는다.
대표 사례와 처리 방식은 `references/failure-handling.md`를 따른다.

## 핵심 원칙 (요약)

1. 재호출은 허용. 단 **도구 / 노드 / 비교 항목** 세 축에서 모두 좁힌다.
2. `get_design_context`는 마지막 수단. fast 모드에선 금지.
3. 응답은 표. 자유 서술 금지.
4. 일치는 카운트, 불일치는 상세.
5. 코드 수정은 안 한다. 메인 에이전트가 후속 흐름에서 처리.
6. **토큰명 매칭 = 일치가 아니다.** `metadata`, `screenshot`, `variable_defs` 중 항목 성격에 맞는 직접 근거가 보고에 1줄씩 없으면 "검증 안 됨"이지 "일치"가 아니다.
7. **scope 힌트는 좁게, 인접 판단은 필요한 만큼만.** "border" 검증 중 직접 연결된 컬럼 구분선/들여쓰기 차이는 `layout-adjacent`로 보고하되, 별도 대규모 검증으로 확장하지 않는다.
8. **`get_metadata`가 인스턴스라 children 미수신** → 시각 판단이 필요한 항목은 `get_screenshot`으로 보완한다. 토큰만 보고 끝내지 않는다.
9. **사용자 시각 힌트 vs sub-agent 관찰 충돌 → 사용자 우선.** sub-agent의 시각 인지는 한계가 있으므로, 사용자가 명시한 시각 요소를 못 봤다면 `layout-adjacent`로 등재하고 deep 모드 권장으로 넘긴다.
