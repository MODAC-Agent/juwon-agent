# Figma Verify Failure Handling

## 목적

`figma-verify` 실행 중 blocker가 보일 때의 상세 처리 규칙이다.
메인 에이전트와 서브에이전트가 같은 판단 기준을 공유하도록 한다.

검증의 본질은 **"무엇이 다른지"를 사용자에게 정확히 알리는 것**이지,
디자인을 재추출하거나 코드를 수정하는 것이 아니다. 책임 경계를 넘는 작업은 거절한다.

## Blocker 케이스

### 검증 대상 코드가 실제로 존재하지 않음

- 전달받은 코드 경로의 파일이 없거나 디렉토리가 비어 있으면 검증을 진행하지 않는다
- "코드 경로 미확정"으로 보고하고 메인 에이전트가 결정하도록 넘긴다

### Figma URL이 유효하지 않거나 접근 불가

- URL 파싱이 실패하거나 MCP 응답이 권한 오류를 반환하면 즉시 중단한다
- 임의로 추정해서 다른 노드를 조회하지 않는다

### 검증 범위가 너무 넓음

- "전체"가 검증 범위인데 코드 트리가 너무 크면(예: 10개 이상의 컴포넌트), fast 모드 한도(MCP 3회) 안에 검증할 수 없다
- 이 경우 `get_screenshot` + `get_metadata` 1회로 **상위 레벨만 점검**하고, 하위는 "범위 초과로 미검증"으로 보고한다
- 사용자에게 "특정 영역 지정"을 권유한다

### MCP 호출 한도 초과

- fast 3회 / deep 5회 한도를 넘어가면 호출을 중단한다
- 미검증 항목을 보고에 명시하고, 추가 호출이 필요하면 사용자 승인을 받도록 한다

### `get_design_context` 호출이 필요해 보일 때 (fast 모드)

- fast 모드에서 `get_design_context`가 필요하다고 판단되면 호출하지 않고 보고로 끝낸다
- "deep 모드 재실행을 권장"으로 표시한다

### 디자인이 명백히 추출 시점 이후 변경됨

- 스펙(`docs/specs/{기능명}/`)의 추출 시점이 오래되었고, 응답에서 노드 구조가 스펙과 다르면 **부분 검증**만 수행한다
- 변경된 영역은 `design-updated`로 분류하고 **재추출(`figma-extract` 수정 모드)을 권유**한다
- verify 단계에서 직접 스펙을 갱신하지 않는다

### 코드가 아직 placeholder 상태

- 코드의 큰 부분이 명백한 placeholder(`TODO`, `Icons.Database` 같은 임시 자산, 빈 구현)면 그 부분은 검증하지 않는다
- 카운트만 보고하고 "자산 확정 후 재검증" 권유

### 응답이 표 형식 제약을 깨뜨릴 위험

- 불일치 항목이 너무 많아 표가 50행 이상으로 늘어나면, **상위 우선순위 항목 20개로 자르고** 나머지는 "추가 항목 N건 (요청 시 표시)"로 표기한다
- 보고 자체가 메인 컨텍스트를 압도하면 안 된다

## blocker가 아닌 경우

다음은 blocker로 보지 않는다:

- 일부 항목이 일치/불일치 판단 모호함 → "확인 필요"로 분류하고 계속 진행
- placeholder가 일부 영역에 있음 → 그 영역만 제외하고 나머지 검증
- 디자인 토큰 매핑이 의도된 차이(`14px` → `text-sm`) → 일치로 처리

## 책임 경계

다음 작업은 verify의 책임이 아니다. 발생 시 명확히 보고하고 후속 흐름으로 넘긴다:

| 상황 | 넘길 곳 |
| --- | --- |
| 디자인이 변경되어 스펙 갱신 필요 | `figma-extract` (수정 모드) |
| 불일치 항목을 코드에 반영 | `figma-implement` (수정 모드) 또는 메인 에이전트의 직접 수정 |
| 새 컴포넌트/새 상태가 추가됨 | `figma-extract` 후 `figma-implement` |
