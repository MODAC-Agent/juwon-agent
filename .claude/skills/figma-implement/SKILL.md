# Figma 디자인 구현 Skill

## 이 Skill의 목적

`figma-extract` Skill로 추출된 스펙 파일들을 참조하여 코드를 구현한다.
구현 세션에서는 Figma MCP를 직접 호출하지 않고, 파일 시스템의 스펙만 참조함으로써
세션 토큰을 절약하고 긴 수정 대화를 가능하게 한다.

> **핵심 규칙:** 이 세션에서 Figma MCP(`get_design_context` 등)를 직접 호출하지 않는다.
> 스펙 파일에 정보가 부족하면, 먼저 `unknowns.md`를 확인하고,
> 정말 필요한 경우에만 최소 범위로 Figma를 재조회한다.

---

## 언제 이 Skill을 사용하는가

- `docs/specs/` 디렉토리에 추출된 스펙 파일이 존재할 때
- 사용자가 "구현해줘", "코드로 만들어줘" 등 구현을 요청할 때
- 이미 추출이 완료된 상태에서 구현을 시작할 때

---

## Step 1: 모드 확인 및 스펙 읽기

`docs/specs/{기능명}/index.md`를 읽고 모드를 확인한다.

### 공통으로 읽는 파일

1. `index.md` (전체 구조 파악, 모드 확인)
2. `unknowns.md` (누락/불확실 항목 파악)

### 모드별 추가 파일

- **신규 모드 (mode: new)**: `tokens.json`을 읽는다
- **수정 모드 (mode: update)**: `tokens-diff.json`이 있으면 읽는다
- **수정 모드 (mode: update)**: `reuse-map.md`를 읽는다

**이 시점에서 개별 상태/변경 파일은 아직 읽지 않는다.** (토큰 절약)

### Step 1-1: 구현 전 스펙 검증

코드를 수정하기 전에 아래 항목을 먼저 점검한다:

- `index.md`, `unknowns.md`가 실제로 존재하는가
- 신규 모드면 `base.md`, `tokens.json`이 존재하는가
- 수정 모드면 `changes/` 디렉토리와 `reuse-map.md`가 존재하는가
- `index.md`에 적힌 상태/변경 파일명이 실제 파일과 일치하는가
- blocker 성격의 미확인 항목이 `unknowns.md`에 남아 있지 않은가

blocker 예시:

- base 상태가 모호함
- 구현에 필요한 핵심 인터랙션 정보가 없음
- 대상 코드 파일 경로가 맞지 않음
- 수정 모드인데 재사용 후보/방침이 비어 있음
- 전역 토큰 변경이 필요한데 사용자 승인 없음

이 단계에서 blocker가 발견되면 **구현을 시작하지 않는다.**
먼저 스펙을 보정하거나, 필요한 최소 범위만 Figma를 재조회한다.

구현 전/중/후 검증의 상세 기준은 아래 reference를 따른다:

- 실패 처리: [references/failure-handling.md](./references/failure-handling.md)
- 검증 및 완료 보고: [references/validation.md](./references/validation.md)

# 신규 모드 (mode: new)

## New-Step 2: 구현 순서 결정

`index.md`의 상태 목록 테이블에서 분류(Base / Delta / Independent)를 확인하고,
다음 순서로 구현한다:

1. **공통 컴포넌트** — `components/` 하위 파일이 있으면 이것부터 읽고 구현한다
2. **Base 상태** — `base.md`를 읽고 기본 UI를 구현한다
3. **Delta 적용** — `deltas/*.md`를 하나씩 읽고 조건부 렌더링/스타일 분기를 추가한다
4. **Independent 상태** — 루트의 독립 상태 파일을 읽고 별도 구현한다
5. **상태 전환 로직** — 상태 간 연결을 구현한다

## New-Step 3: Base + Delta 구현

### Base 구현

1. `base.md`를 읽고 기본 상태의 전체 UI를 구현한다
2. 이 코드가 모든 Delta의 기반이 되므로, 조건 분기가 들어갈 위치를 고려하며 구조를 잡는다

### Delta 적용

각 Delta를 적용할 때:

1. `deltas/{상태명}.md`를 읽는다 — **변경분만 기록되어 있으므로 파일이 작다**
2. 변경 항목을 보고, base 코드에 조건부 렌더링/스타일 분기를 추가한다
3. 다음 Delta로 넘어간다

Delta 적용 시 코드 패턴 예시:

```tsx
{/* Delta: checked 상태에서 DetailPanel 표시 */}
{isEmailEnabled && (
  <div className="flex flex-col gap-3 p-4 border-t">
    <label className="text-sm font-medium text-gray-700">알림 빈도</label>
    <select className="h-9 border rounded-md w-full">...</select>
  </div>
)}
```

### Independent 구현

독립 상태 파일은 전체 트리가 포함되어 있으므로, base와 별개로 구현한다.
예: 모달, 전혀 다른 레이아웃의 화면 등

# 수정 모드 (mode: update)

## Update-Step 2: 기존 코드 읽기

`index.md`에 명시된 **대상 코드 위치**의 파일들을 읽는다.
이 코드가 base(현재 main 상태)이다.

이어서 `reuse-map.md`의 재사용 후보를 확인한다:

1. 후보 컴포넌트의 public API와 props를 읽는다
2. 변경 파일을 적용할 때 기존 후보로 표현 가능한지 먼저 판단한다
3. 새 컴포넌트/새 스타일 래퍼를 만들 경우, 기존 후보로 부족한 이유를 최종 보고에 남긴다
4. `legacy/` 후보는 저장소 규칙상 새 코드에 직접 추가하지 않고, 필요하면 `src/` public API로 이전하는 별도 작업으로 분리한다

## Update-Step 3: 변경 사항 적용

`changes/` 디렉토리의 파일을 하나씩 읽으며 적용한다:

1. 변경 파일(예: `changes/header-layout.md`)을 읽는다
2. 해당 파일에 명시된 대상 코드와 재사용 방침을 확인한다
3. 현재 코드와 변경 내용을 비교해 실제로 바뀌는 부분만 수정한다
4. 다음 변경 파일로 넘어간다

**핵심:** 현재 코드가 base이므로, 변경 스펙은 "무엇을 바꿔야 하는지"만 담고 있다.
PR의 diff를 보고 코드를 수정하는 것과 동일한 흐름이다.

금지:
- 대상 컴포넌트를 Figma 스펙 기준으로 통째로 재작성
- 기존 컴포넌트 props/variant로 가능한 UI를 새 컴포넌트로 중복 구현
- `changes/*.md`에 없는 영역을 "정리" 명목으로 리팩터링

### 새로운 요소/상태 추가

변경 파일에 "새로운 상태" 섹션이 있으면, 이는 full spec으로 기술되어 있다.
(코드에 비교 대상이 없으므로 diff가 아닌 전체 명세)

이 경우 신규 모드의 구현 방식과 동일하게 처리한다.

### 토큰 변경 적용

`tokens-diff.json`이 있으면 `scope`를 확인한다:

- **`scope: "local"`** (기본): 해당 기능의 코드에만 새 값을 적용한다. 프로젝트 전역 디자인 시스템(CSS variables, theme config)은 수정하지 않는다.
- **`global_candidates`**: 전역 변경이 필요한 항목이 있으면 사용자에게 알리고 승인을 받은 후에만 적용한다.

적용 방법:
- `changed`: 해당 기능 코드 내에서 기존 값을 새 값으로 교체
- `added`: 해당 기능 코드에서 새 토큰 값 사용

# 공통 워크플로우

## 디자인 토큰 -> 코드 매핑

스펙 파일의 정확한 수치를 코드로 옮길 때, 다음 우선순위를 따른다:

| 우선순위 | 방법 | 설명 |
| -------- | ---- | ---- |
| 1순위 | 프로젝트 기존 디자인 시스템 | CSS variables, theme tokens 등 |
| 2순위 | Tailwind 기본 유틸리티 클래스 | 가장 가까운 값으로 매핑 |
| 3순위 | Arbitrary value | 위 두 가지로 표현할 수 없는 경우에만 |

예시:

- 스펙: `font-size 14px` -> 코드: `text-sm` (Tailwind 기본값)
- 스펙: `gap 24px` -> 코드: `gap-6` (Tailwind 기본값)
- 스펙: `width 347px` -> 코드: `max-w-sm` 또는 `w-full` (레이아웃 의도 파악 후 결정)
  - 347px 같은 값은 대부분 컨테이너에 맞춘 결과이지 의도된 수치가 아니다
  - 정말 고정 크기가 의도된 경우에만 `w-[347px]` 사용

**arbitrary value(`w-[347px]` 같은)는 최후의 수단이다.**
스펙에 적힌 수치가 "의도된 고정값"인지 "레이아웃 결과값"인지 판단한다.

## 수정 대화

사용자가 수정을 요청하면:

1. 수정 대상이 **어떤 스펙 파일에 해당하는지** 파악한다
   - 신규 모드: Base / Delta / Independent 중 어디?
   - 수정 모드: changes/ 중 어떤 파일?
2. 해당 스펙 파일만 읽는다
3. 코드를 수정한다

**절대로** "전체 스펙을 다시 확인하겠습니다"라며 모든 파일을 읽지 않는다.
관련 파일만 최소한으로 참조한다.

영향 범위 확인이 필요한 경우:

- 공유 컴포넌트 수정 -> 해당 컴포넌트를 사용하는 다른 스펙 확인
- 레이아웃 구조 변경 -> `index.md`의 공통 레이아웃 확인
- 디자인 토큰 변경 -> `tokens.json` 또는 `tokens-diff.json` 확인 후 일괄 적용

## 스펙과 코드의 충돌 처리

구현 중 스펙과 다르게 코드를 작성해야 하는 상황이 생길 수 있다.

이 경우 다음 규칙을 따른다:

1. **스펙의 수치가 기술적으로 불합리한 경우** (예: 반응형에서 고정 px이 레이아웃을 깨뜨림)
   -> 합리적인 대안으로 구현하되, 사용자에게 차이점과 이유를 **반드시** 알린다.
2. **스펙에 없는 인터랙션을 추가해야 하는 경우** (예: 키보드 접근성)
   -> 추가하되, 사용자에게 "스펙에는 없지만 추가했다"고 알린다.
3. **어떤 경우에도** 사용자에게 알리지 않고 스펙을 무시하지 않는다.

---

## Figma MCP 재호출이 필요한 경우

다음 상황에서만 Figma MCP를 다시 호출한다:

- `unknowns.md`에 기록된 항목 중, 구현에 반드시 필요한 정보가 있을 때
- 사용자가 "Figma에서 다시 확인해줘"라고 명시적으로 요청할 때
- 디자인이 변경되어 스펙을 업데이트해야 할 때

재호출 시 반드시:

1. 필요한 노드/컴포넌트만 조회한다 (페이지 전체 재조회 금지)
2. 조회 결과로 스펙 파일을 업데이트한다
3. `unknowns.md`에서 해결된 항목을 체크 표시한다
4. 업데이트된 스펙 파일을 기반으로 코드를 수정한다

대표 사례와 처리 방식은 `references/failure-handling.md`를 따른다.

## 구현 후 검증

코드 수정이 끝나면 가능한 범위에서 검증을 수행한다.
검증 항목과 보고 형식은 `references/validation.md`를 따른다.

## 구현 완료 보고 (마무리 단계)

모든 스펙 파일의 구현이 끝나면, 다음 **스펙-코드 불일치 보고**를 사용자에게 제시한다.
이 보고는 구현 과정에서 스펙과 다르게 처리한 부분을 사용자가 한눈에 검토할 수 있게 한다.

상세 템플릿은 `references/validation.md`를 따른다.
**이 보고를 생략하지 않는다.** 변경/추가/미구현이 모두 없으면 "모두 스펙대로 구현 완료"라고 명시한다.

> **Figma-코드 일치 검증이 필요하면** `/figma-verify`를 안내한다. `figma-implement`의 보고는
> "스펙 대비 차이"이고, `figma-verify`는 "Figma 원본 대비 차이"이다. 디자인이 추출 이후
> 변경되었을 가능성이 의심되거나, 사용자가 "정말 디자인과 일치하는지 확인해줘"라고
> 요청하면 verify로 넘긴다.

## 핵심 원칙

1. 구현 세션에서 Figma MCP를 직접 호출하는 것을 **최대한 피한다**. 이것이 이 Skill의 존재 이유이다.
2. 스펙 파일을 읽을 때는 **필요한 파일만, 필요한 시점에** 읽는다.
3. `tokens.json`/`tokens-diff.json`의 값을 코드에 일관되게 적용하되, 프로젝트 디자인 시스템에 맞게 매핑한다.
4. **arbitrary value 남발을 피한다.** 스펙 수치를 그대로 px로 옮기는 것은 좋은 구현이 아니다.
5. 수정 요청 시 영향 범위를 먼저 판단하고, 관련 파일만 참조한다.
6. 스펙과 코드 사이에 차이가 생기면, 그 이유를 사용자에게 **반드시** 알린다.
7. **수정 모드에서는 현재 코드가 base다.** 코드를 먼저 읽고, changes 스펙의 diff만 적용한다.
8. **수정 모드에서는 기존 컴포넌트 재사용이 기본값이다.** 새 구현은 `reuse-map.md`의 판단과 최종 보고로 정당화한다.
